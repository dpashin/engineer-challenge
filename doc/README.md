#### Ключевые инварианты и бизнес-правила

##### Правила reset-token
1. Срок действия (Expiration): 10 минут
2. Одноразовость (Single-use)
- Аннулирование после использования: Сразу после успешной смены пароля токен должен быть немедленно удален или помечен как недействительный.
- Аннулирование при новом запросе: Если пользователь запрашивает сброс пароля повторно, все предыдущие токены для этого аккаунта должны быть отозваны. 
3. Криптографические требования
- Случайность: Токен должен генерироваться с помощью криптографически стойкого генератора псевдослучайных чисел (CSPRNG). Нельзя использовать обычные функции типа rand().
- Длина и энтропия: Минимум 128 бит энтропии (обычно это строка от 22 до 32+ символов в формате Base64 или URL-safe).
4. Хеширование в БД: В базе данных следует хранить не сам токен, а его хеш (например, SHA-256).

##### Валидация пароля
1. Минимальная длина: 8 символов.
2. Разнообразие символов: Требование использовать минимум по одному символу из разных групп:
- Заглавные буквы (A-Z).
- Строчные буквы (a-z).
- Цифры (0-9).
- Специальные символы (!, @, #, $, % и др.).

##### Rate limiting

- Если пользователь вводит присланный код неправильно несколько раз (3 попытки), возможность запроса нового кода блокируется на длительный срок (30 минут).

- [ ] Ограничения на повторный запрос токена восстановления пароля.

- [ ] Ограничения на отправку неверного токена восстановления пароля.

- [ ] Ограничения на неверную отправку токена восстановления.


##### Очистка устаревших данных

Следующие устаревшие сущности должны удаляться по крону через неделю после того, как у них истек срок действия:
- password_reset_tokens
- password_reset_attempts
- refresh_tokens

В случае, если бэкэнд развернут на нескольких инстансах, не должно возникать конфликтов в крон-задачах.
